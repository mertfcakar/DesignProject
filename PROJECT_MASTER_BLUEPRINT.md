## 1. System Vision

A real-time **Music Emotion Recognition (MER)** + **Music Auto-Tagging** system that drives a professional-grade live concert lighting rig in Unreal Engine 5.7 from live audio input.

The system performs three classes of analysis in parallel:

- **Multi-label tagging** (195 tags across genre / mood / instrument) via a VGGish + LSTM classifier
- **5-D affective vector** (Arousal, Valence, Timbre, Rhythm, Intensity) from the same model's bottleneck
- **Low-level DSP** (RMS, bass/mid/treble, kick/snare/hi-hat onset detection) computed in C++ from the raw audio buffer

Outputs drive a stage with 6 wash lights, 4 beam lights, 4 strobes, 2 side spots, 4 floor lights, and 5 instrument-pinpoint spots, all running genre-aware scene presets.

## 3. The Three Computational Layers

### Layer I — Audio Capture + DSP (C++ in UE5)
- Submix buffer listener, 48 kHz stereo → mono → ring buffer
- Custom C++ mel-spectrogram (matches VGGish exactly: 400-sample window, 160 hop, 512 FFT, 64 mel bins, triangular HTK filterbank, magnitude not power, log-mel without normalization, time-major layout)
- Per-band energy: bass (0-8 mel bins), mid (16-40), treble (48-64)
- Onset detection on bass/mid/treble band derivatives → kick / snare / hi-hat flashes
- Threadsafe atomics for inter-thread communication

### Layer II — ML Inference (Python sidecar primary, UE5 fallback)

**Python sidecar (preferred path, ~Python-equivalent quality):**
- `sounddevice` captures from VoiceMeeter Out B1
- VGGish (with PCA postprocessing) → 128-dim quantized embeddings
- StatefulMusicBottleneck LSTM → 195 sigmoid tag probabilities + 5-D bottleneck
- EMA smoothing (alpha = 0.15) for stable top-K selection
- UDP JSON broadcast to UE5 on `127.0.0.1:17777`

**UE5 in-engine pipeline (fallback if sidecar offline):**
- Custom C++ mel + VGGish ONNX
- PCA postprocessing in C++ (`VGGishPCAConstants.h`, generated by `export_vggish_pca.py`)
- Z-score normalization with training stats (`NormalizationConstants.h`)
- AestheticBrain_v2.onnx (4 outputs: tag_probs, aesthetic_vector, h_n, c_n)
- Stateless mode (LSTM state zeroed each frame to avoid runaway saturation)

### Layer III — Stage Lighting (C++ in UE5)
- 8 base scenes (Warm, Cool, Neon, Chase, Strobe, Spotlight, Burst, Rainbow)
- Scene picker: biased by detected genre when sidecar is active, falls back to affective scores otherwise
- Per-genre color palette (red/orange for rock, magenta/cyan for electronic, warm white for classical, etc.)
- Per-instrument light boost (drums detected → drum spot brighter; piano detected → piano spot brighter; etc.)
- Onset-driven flashes (kick → wash + floor boost, snare → side lights, hi-hat → guitar spot)
- Silence fade for graceful idle behavior

## 4. Project History — What We Tried and Why We Changed

### 4.1  Original architecture (pre-2026-05-09)
- All inference in UE5 via NNE/ONNX
- Custom C++ mel spectrogram (simplified: nearest FFT bin per mel, power not magnitude, per-spectrogram normalization, transposed tensor layout)
- ONNX export used `InferenceWrapper` that returned only the 5-D bottleneck — **discarded the 195-tag classifier output entirely**
- UE5 displayed the 5 bottleneck dims as "Arousal/Valence/Timbre/Rhythm/Intensity" — these labels were not actually trained meanings, just compressed features
- Result: model output collapsed to constant predictions; both Bach and Queen produced identical scores

### 4.2  Diagnostics that exposed the issues
- `test_genre.py` — tested the trained model on 8 known songs in pure Python. Got 87 % top-3 accuracy. Confirmed the model itself is good
- `diagnostic_pca.py` — ran each test song through VGGish with and without PCA postprocessing. Without PCA, all 8 songs produced identical "electronic 53.7 %" output regardless of input. **Confirmed PCA is required**
- Code review found: z-score normalization (`NormalizationConstants.h`) was generated but never `#include`d in C++; mel spectrogram had power instead of magnitude, single-bin filterbank instead of triangular, transposed layout

### 4.3  Iterative fixes (in order)
1. **InferenceWrapper v2** — return both tag probabilities and the bottleneck (`export_onnx_v2.py`)
2. **PCA postprocessing in C++** — matmul + clip + 8-bit quantize (`VGGishPCAConstants.h`)
3. **Z-score normalization in C++** — apply `(x - mean) / std` after PCA
4. **Proper mel spectrogram** — magnitude (not power), triangular filterbank via precomputed matrix (`VGGishMelConstants.h`), removed per-spectrogram normalization, fixed time-major tensor layout
5. **LSTM stateless mode** — zero the hidden/cell state each inference (the trained weights cause runaway saturation when state accumulates)

After step 5, UE5 produced musically appropriate predictions but still ~10 percentage points off from Python's accuracy due to numerical precision differences in the FFT and the audio path through VoiceMeeter.

### 4.4  Hybrid sidecar architecture (current)
- `python_sidecar.py` runs the proven Python pipeline live and broadcasts predictions over UDP
- `AffectiveAudioActor` listens on port 17777, parses JSON, exposes top genre/mood/instrument as getters
- `ConcertStageDirector` reads those getters and applies genre-aware scenes + instrument boost
- The in-engine UE5 ONNX path remains as a fallback when the sidecar is not running
- Verified end-to-end on Metallica (Master of Puppets): UE5 displays `[PY] GENRE: ROCK 49 %`, `MOOD: ENERGETIC`, `INSTR: BASS 46 %` — within 10 points of pure-Python results. Lighting palette switches to red/orange wash with strobes.

## 9. Architectural Decisions Worth Documenting in the Report

- **Why Python sidecar instead of pure UE5?** UE5's NNE plugin runs ONNX, but reproducing VGGish's input pipeline (windowed STFT, magnitude spectrogram, triangular mel filterbank, PCA whitening, 8-bit quantization) byte-for-byte in C++ proved fragile; small numerical differences cascade through the LSTM and flip top-1 predictions. The Python pipeline is the reference implementation and runs in <50 ms on consumer GPU. Splitting inference (Python) from rendering (UE5) is industry-standard for ML-driven applications and made debugging tractable.
- **Why keep the in-engine ONNX path?** As a graceful fallback if the user does not want to run a second process, and to demonstrate that UE5's NNE plugin is functional. The fallback produces musically appropriate output even if not exactly Python-equivalent.
- **Why stateless LSTM in the UE5 path?** Empirically, when the LSTM state accumulates across frames in the UE5 numerical environment, the output saturates and stops responding to new input. Resetting the state each inference produces dynamic predictions that vary with audio content. This is a discovered finding worth reporting; the Python path uses persistent state with no such issue, suggesting the UE5 fallback's input distribution is just different enough to push the LSTM into an unstable regime.
